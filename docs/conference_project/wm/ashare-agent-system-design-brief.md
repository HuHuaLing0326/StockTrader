## 二、业务背景与目标

### 2.1 用户与场景

- 使用者是个人投资者，A 股新手，普通账户权限。
- 系统用于**研究和模拟交易**：不接真实券商，不真实下单，不动真钱。
- 日常使用方式是"系统无人值守自动运行，我只阅读报告"。命令行只用于安装、排障和手工补跑，不是日常界面。
- 模拟账户初始资金：【待填，参考系统为 1 万元人民币】。

### 2.2 目标

1. **主要目标**：辅助选股，追求相对基准（沪深 300）的超额收益。
2. **前提目标：结论必须可检验**。系统必须能用客观数据回答"它的推荐到底有没有跑赢基准、跑赢随机选股"。没有这个能力，第 1 条无从谈起。
3. **约束**：任何时候都不能用未来数据、不能编造数据、不能悄悄降级。宁可不做决策，也不做依据不可靠的决策。

### 2.3 必须清醒认识的事实

- 公开的大模型交易智能体研究中，多数报告的收益在受控重新评估后站不住。例如有的论文原文报告 +23%，受控重评后变成 −22%；也有研究发现所谓收益主要来自市场或风格的被动暴露。
- 因此本系统的设计重心是"**如何证明自己有没有在赚钱、以及如何防止自己骗自己**"，选股方法本身是在这个框架内反复检验和迭代的对象。

## 三、参考系统概况

### 3.1 规模与形态

- 约 12 万行 Python 代码，约 2200 个测试；运维命令行有上百个子命令。
- 常驻后台的守护进程，内含约 30 个定时任务，全天候运行。
- 平台为 Windows，由系统服务托管，开机自启、崩溃自动重启。

### 3.2 技术栈

| 层面 | 参考系统使用的技术 |
|---|---|
| 语言与包管理 | Python 3.13，uv 锁定依赖 |
| 分析引擎 | TradingAgents-CN（开源多智能体股票分析框架，基于 LangGraph），外面再套一层自建的多智能体运行时 |
| 大模型 | 兼容 OpenAI 接口的模型服务，按任务重要性分级路由 |
| 本地模型 | 中文金融情绪模型 FinBERT（CPU 运行），只用于给新闻标题打情绪分 |
| 存储 | DuckDB 存交易和研究账本；运行时状态可选 MySQL；SQLite 全文检索（FTS5）做记忆检索，不用向量库 |
| 调度 | APScheduler 线程池；耗时的正式分析放在独立子进程里，卡死时可以单独终止 |
| 数据 | akshare、baostock、Tushare、mootdx（通达信协议）、腾讯和新浪行情接口、东方财富、巨潮、同花顺、问财 |
| 抓取 | requests、trafilatura（正文提取）、feedparser（RSS）、pypdf、可选的浏览器自动化 |
| 配置与校验 | pydantic：所有配置项显式声明，带取值范围校验 |
| 交付 | Markdown 报告、邮件、飞书/企业微信/Telegram 推送 |
| 质量 | pytest、hypothesis（属性测试）、ruff，持续集成 |

## 四、参考系统的功能与实现方式

### 4.1 每日运行节奏（北京时间，只在核实为交易日时执行交易相关任务）

| 时间 | 任务 |
|---|---|
| 08:45 | 盘前刷新数据 |
| 09:45、10:30，另外盘中每 10 分钟 | 执行待成交的模拟订单 |
| 10:00、11:45、14:30 | 盘中只读巡检：持仓、权益、挂单（不调用大模型、不下单） |
| 10:05、13:10、14:35 | 盘中决策：消费已排队的交易信号，通过组合闸门后下单 |
| 15:20 | 收盘复盘：按市价估值、更新推荐结果、运行对照组和止损线 |
| 15:35 | K 线特征快照 |
| 15:40 | 决策流水线：审阅研究草稿 → 组合计划 → 订单闸门 |
| 16:30 | 完整的每日分析周期 |
| 18:30 起，至次日 09:15 | 主题持续研究：主题 → 个股线索 → 子调查任务 |
| 全天 | 新闻脉冲（每 150 分钟，不看日历）、情绪打分、数据源恢复探测、大模型可用性监控、心跳 |
| 周期性 | 每日数据库导出与容量检查、每周归档、周报和月报 |

### 4.2 数据采集

详见独立的数据采集需求文档。要点如下：
- 多数据源冗余：交易日历、日线、快照、报价都有两个以上来源，按优先级切换，并标注实际来源。
- 防封禁：东方财富按 IP 限流，所有请求都经过节流和断路器。
- 交易日历必须核实，核实不了就禁止交易。
- 缓存只存已定型的数据；不允许悄悄用旧缓存顶替实时数据。
- 所有数据按决策时点过滤；每次采集都写入健康台账。

### 4.3 大盘状态判断

- 用沪深 300 指数近 90 天日线计算 5、20、60 日均线和 20 日收益，再加上全市场上涨家数占比，汇总成一个分数。
- 按分数分为四档：强势（≥2.5）、震荡、弱势（<0）、高风险（≤−2）。
- 大盘状态只能**降低**仓位上限，不能产生买入信号。

### 4.4 候选股票初筛

1. **动态初筛**：取全市场快照 → 按账户交易权限过滤 → 剔除买不起一手的 → 按流动性和趋势排出短名单（默认 40 只）。
2. 全市场快照拿不到时**直接停止**，不做决策；不会退回到固定股票池。
3. **最终候选默认 5 个名额，按固定分道分配**：
   - **回调分道**：最多 2 个名额，从 12 个候选中挑选，成交额至少 3 亿元。使用 60 日涨幅的全市场排名（RPS）。排名数据缺失时，只接纳当日跌幅在 0 到 −3.5% 之间、且当日收益处于全市场第 20 至 60 百分位的高流动性股票。
   - **宽基 ETF 分道**：最多 1 个名额，默认标的是沪深 300 ETF。只在强势市场开放；震荡市场需要同时满足三个条件：大盘分数 ≥2.0、上涨家数占比 ≥70%、基准当日收益 ≥0.1%。
   - **其余名额**归普通股票池。
   - 分道里技术分不达标的名额，退回普通股票池。
4. 前几天的候选可以延续（默认最多 3 天、3 只）。
5. **初筛只决定"谁值得研究"**。入选不会直接产生订单，后面还要经过全部研究和闸门。

### 4.5 研究证据

1. **分类采集**：对每只候选股票按类别采集材料，包括公司资料、公告全文、财务、资金流、筹码与资本事件、一致预期、研报、个股新闻、网页新闻、行业新闻，以及宏观、政策、海外动态。
2. **文本类材料不直接给决策模型看**：
   - 由搜索智能体完成"搜索 → 抓取正文 → 大模型抽取论断"；
   - 每条论断必须带原文逐字引文，程序校验引文确实存在；
   - 第二次大模型调用复核引文是否支持论断；
   - 支持率低于 80% 的整条丢弃。
3. **组装证据包**：
   - 材料按类别分组：市场、宏观、政策、海外、行业、公司、财务、公告、资金流、新闻；
   - 每条按来源打可信度分（1–5）和垃圾度分（1–5）；
   - 明确列出数据缺口。
4. **注入决策模型时附带规则**："单条公告、单条新闻、单次资金流或单个财务指标，不得机械触发买卖。"资金流和北向数据只视为市场参与者的行为信号，不视为政策意图的证据。
5. **外部文本一律视为不可信**：清除隐藏字符，用边界标记包裹，每行加数据标记，防止提示注入。

### 4.6 多智能体分析

**正式分析引擎（TradingAgents-CN）**
- 启用市场、新闻、基本面三类分析师，然后进行多空研究员辩论（1 轮）、交易员决策、风险讨论（1 轮）。
- 外层按角色注入各自的上下文包，避免所有角色吃同一大块证据。
- 给产生交易动作的角色额外注入账户执行约束：现金、在途资金、交易权限、持仓批次、T+1 可卖数量。这只是提示信息，最终以券商和闸门的复核为准。
- 每个角色单独输出一个概率：**未来 20 个交易日跑赢沪深 300 的概率**。格式为严格 JSON，只含角色、概率、不超过 160 字的依据。

**自建的持久化研究团队**（团队、成员注册、邮箱、交接、会话、步骤全部落库）

| 角色 | 职责 |
|---|---|
| 数据质量审计 | 检查数据新鲜度、来源和数据源健康状况 |
| 盘面解读 | 指数状态、市场宽度、流动性、换手、资金流 |
| 宏观政策解读 | 宏观、政策、全球风险 |
| 行业解读 | 板块轮动、产业链、拥挤度、主题证据 |
| 公司基本面解读 | 公司事实、公告新闻、财务红旗、分红 |
| 同业对比 | 估值、资金流和可比公司 |
| 日历与执行守卫 | 交易日、交易时段、T+1、费用、整手、新手账户限制 |
| 风险复核 | 独立挑战主论点，可以否决仓位 |
| 组合协调 | 结合账户状态起草模拟交易计划 |
| 中文笔记 | 撰写简洁的中文结论，不改变决策 |

**执行顺序**：数据质量审计 → 各专家并行 → 日历守卫 → 风险复核 → 组合协调 → 中文笔记。下游角色消费上游的结构化交接结果，不重读全部原始材料。

**概念区分**：
- 定时任务只负责"何时运行"，不是智能体；
- 一个组件要称为"智能体"，必须同时具备六项：角色身份、明确的工具范围、有界的输入上下文、结构化输出格式、持久化的会话记录、明确的后续工作归属；
- 子智能体默认不得再派生新的智能体。

### 4.7 决策流水线（从研究到订单）

1. **持续研究**：按配置的主题篮子，每个主题生成一个市场研究任务 → 展开成个股线索 → 为每只个股生成只采集证据的调查任务。
2. **研究草稿**：调查任务产出研究草稿，这时还不是推荐。
3. **草稿审阅**：保守的风险和证据闸门。同一股票、同一日期如果最近有关键行情数据失败，偏买入的草稿一律暂缓，直到障碍消除。
4. **收盘后初筛**：
   - 对候选逐只做一次大模型初筛，结论分为推进、观察、拒绝、受阻四种；每轮最多做 5 个新初筛；
   - **证据截止点固定为该交易日收盘**，此后的证据一律禁止使用；
   - "推进"优先进入正式分析；有余量时由排名最高的"观察"补位；"拒绝"和"受阻"永不进入。
5. **正式分析**：大模型深度分析，每只候选在独立子进程中运行，默认最多 2 个并发。超过 7 天未完成的旧草稿标记为过期，需要重新研究。
6. **组合计划**：结合账户状态，检查单股推荐、现有持仓、在途订单和大盘状态是否一致；仓位按大盘状态重新封顶。组合计划本身不下单。
7. **订单闸门**：
   - 可以只演练（dry-run），也可以真正生成订单；
   - 真正下单前重新读取现金、持仓、在途订单和执行价格；
   - 订单记录审核通过的具体股数，执行时不按模糊的目标比例重算。
8. **盘中信号收件箱**：
   - 收盘后形成的交易计划进入持久化收件箱；
   - 有效期取"36 小时"与"下一个已核实交易日收盘"中较晚的一个，这样周五盘后的推荐周一开盘仍可处理；
   - 过期信号标记为"已过期拒绝"，不删除；
   - 盘中决策只在已核实的连续竞价时段内消费信号；
   - 没有信号时只做保守动作（持有、监控挂单、复核持仓风险），**绝不因为大盘强就凭空生成个股买单**。
9. **事件触发**：对持仓或计划中的股票，出现高重要度事件时自动创建针对性的调查任务。

### 4.8 模拟券商与账本

1. **下单与成交时间**：
   - 收盘后的决策只生成待成交订单；
   - 订单记录决策时间、市场时段、交易日历来源和最早可执行日；
   - 默认在下一个交易日按开盘价成交。
2. **订单阻断**：交易日历无法核实时，订单被阻断。
3. **A 股规则**：
   - 一手 100 股起买；不能做空（没有持仓的卖单直接忽略）；
   - T+1：当天买入次日才可卖；
   - 开盘涨停买不进，跌停卖不出；
   - 滑点默认万分之五，并且不能越过涨跌停价。
4. **费用**：
   - 佣金 0.03%，最低 5 元；
   - 过户费 0.001%；
   - 印花税 0.05%，只在卖出时收；
   - ETF 不收印花税。
5. **持仓批次与分红**：
   - 按先进先出记录持仓批次；
   - 现金分红按税前金额入账，并按持有期估算递延红利税，在卖出对应批次时结算；
   - ETF 分配在模型中视为免税。
6. **估值**：所有持仓都必须有目标日的准确价格，否则当日估值记为不可用，不做估算。
7. **成交后自动审计**：成交日不得早于最早可执行日；开盘成交价要和当日开盘价对得上；费用要符合费率；必须有对应的成交记录和批次记录。
8. **多账户设计**：主账户、对照组账户、实验账户共用同一套券商规则。所有涉及订单、成交、账户的查询都必须带账户名。

### 4.9 风控与适当性

1. **仓位上限随大盘状态变化**：

   | 大盘状态 | 单票仓位上限 |
   |---|---|
   | 强势 | 20% |
   | 震荡 | 14%（正常上限的 70%） |
   | 弱势 | 5% |
   | 高风险 | 0，不新增仓位 |

2. **资金纪律**：
   - 权益回撤到初始资金的 80% 时，暂停自动买入；
   - 跌到初始资金的 70% 时，硬性停止；
   - 卖出始终允许；亏损后不自动补钱。
3. **交易权限**：实际可用权限 = 配置的券商权限，再按账户资产和交易经验动态收紧。1 万元的新手账户只开放沪深主板和 ETF，即使配置里误加了创业板、科创板也无效。
4. **确定性守卫**（用代码否决 prompt 管不住的情况）：
   - **数据质量门**：数据质量结论不是"可信"时，组合协调的交易动作被强制改为"不操作"；
   - **ST 风险标记**：每日从快照中的股票名称刷新风险警示状态；
   - **基本面红旗**：用三大报表的数字确定性计算。原则是缺数据不拦截，只有红旗被数据确认时才否决；
   - **文本信号**：必须有出处。
   - 原则：**大模型负责解释，代码负责否决**。

### 4.10 评估体系

1. **观察窗**：修复已知数据缺陷之前的结果视为污染数据，不参与结论，原始数据保留。
2. **对照组账户**（与主策略走同一个模拟券商）：

   | 对照组 | 行为 |
   |---|---|
   | 买入持有 | 首次用全部现金买入沪深 300 ETF，此后不再交易 |
   | 随机选股 | 每周从同一个候选池按日期种子随机抽 3 只，重新平衡 |
   | 等权排名 | 每周持有排名前三的候选，等权 |

   对照组账户绝不能和主策略共用镜像订单。
3. **执行实验账户**：只改变执行政策、不额外调用大模型，用来比较不同仓位规则：
   - 单票上限 20%；
   - 每笔固定 20%；
   - 激进档；
   - 按 1 股为增量的账户，用来量化"整手"约束的影响。
4. **独立策略账户**：共享研究结果，但独立做决策，例如"早期试探低吸"和"确认后入场"两种入场政策。
5. **预先登记的止损线**：门槛在实验开始前定好，只许收紧，不许放松；样本不足时只报告"信息不足"，不发假警报。
6. **概率评分**：
   - 每条推荐都有"未来 20 日跑赢沪深 300"的概率，不依赖是否成交，因此每条推荐都是评估样本；
   - 用 Brier 分数、Murphy 分解、可靠性曲线评估各角色的校准度；
   - 再校准规则必须经过正式审查才能生效。
7. **小样本统计**：
   - Jeffreys 收缩，即 (命中数 + 0.5) / (样本数 + 1)；
   - 可随时查看的 e 值序贯检验；
   - 对多重检验打折的夏普比率（DSR）和最短业绩记录长度（MinTRL）。
8. **前瞻收益与归因**：按 1、3、5、10、20 日跟踪推荐的结果。按证据类别和来源做归因，但只视为线索，不视为因果证明。
9. **回放与消融**：
   - 冻结输入、提示词、模型和版本后重新运行决策，用动作翻转率和一致性系数（Kappa）衡量变化；新版本相对旧版本的翻转率不超过 15% 才允许上线；
   - 辩论轮数消融；
   - 实体遮蔽泄漏审计：把股票代码、名称、日期匿名化后重跑。

### 4.11 记忆与学习

1. **两阶段记忆管道**：
   - **第一阶段**：从闲置 2 小时以上的已完成任务中抽取候选记忆。"无可记"是首选结果；写入时脱敏密钥。
   - **第二阶段**：每日汇总成记忆文件，并记录每条记忆的使用次数，形成反馈。
2. **记忆按耐久性分为三类**：操作规则、持久事实、情景事件。情景事件超过 5 天不再进入决策召回。
3. **检索方式**：使用全文检索，不用向量检索。
4. **学习反馈**：根据模拟交易的结果生成校准笔记，小样本标注为"暂定"。它只作为弱参考，不得变成硬性交易规则，也不是模型训练。

### 4.12 智能体基础设施

1. **统一的工具注册表**：
   - 每个角色只看到自己的工具包。工具包是聚焦注意力的手段，不是权限控制；
   - 参数不合法时，返回错误观察结果让模型修正，而不是抛异常中断。
2. **三层上下文管理**：
   - 记录时截断：超大的工具结果另存为附件，只保留预览；
   - 较早的工具结果在视图中折叠成摘要，原始记录完整保留；
   - 最后用总预算兜底。
3. **状态重注入**：通过类型化的附件，把日期变化、同伴交接增量、数据缺口提醒等状态重新注入上下文。
4. **会话笔记压缩**：
   - 笔记使用固定的中文七节模板：当前结论、证据状态、已排除假设、数据缺口、关键数字、下一步、工作日志；
   - 压缩失败就中止，**不允许直接截断顶替**。
5. **技能（SOP）两级披露**：常驻提示里只列名称和描述，需要时再展开全文。参考系统内置四个：基本面排雷、收盘复盘、异常排查、盘中信号复核。
6. **钩子**：工具调用之后、任务结束时可以运行外部命令；退出码 2 表示拦截。

### 4.13 大模型使用规则

1. **大模型可用是运行前提**：
   - 每轮工作前先探测，不可用就整轮跳过并告警；
   - 运行中途断开时，释放已领取的任务，留给下次执行，不判为失败；
   - **绝不在没有大模型的情况下硬跑，也不用规则兜底冒充**。
2. **按任务重要性分级路由**：简单任务走快速模型，重要任务走强模型并配有后备链。用到后备模型时，必须在结论上打"模型降级"标记。
3. 记录每次调用的 token 用量和成本。

### 4.14 自动运行与可靠性

1. **持久化工作流**：
   - 每次调度都记一本"准入、日历、任务"三步台账，重启后复用已完成的步骤；
   - 每次重试都重新检查准入，让暂停和停止指令不能被绕过；
   - 邮件和推送走发件箱去重。
2. **错过与失败的补救**：
   - 错过 30 分钟以内的任务会补跑，积压的触发合并成一次；
   - 每日分析失败时，每 15 分钟检查一次，回溯 14 天，从断点续跑。
3. **运行控制**：可以按层暂停或恢复（研究、决策、执行），已排队的决策不会丢失。
4. **自我监控**：
   - 数据源故障自动探测恢复；
   - 告警分级处理：低成本的恢复动作自动执行，高成本的需要显式授权；
   - 每次部署后必须跑冒烟测试。

### 4.15 报告与通知

- 日报、收盘报告、周报和月报（按资金流入流出调整收益），以中文 Markdown 生成并发邮件。
- 新告警、排单、成交即时推送，每小时有上限，防止刷屏。
- 推送失败不影响主流程。

## 五、参考系统的实测经验与教训

### 5.1 策略与评估

1. **信息相同时，辩论增益很小**：同一批报告，0 轮与 1 轮辩论相比，20 个场景中只有 2 个改变了动作（翻转率 10%，Kappa 0.74）。要让辩论有用，应给多空双方分配**不同的证据子集**。
2. **模型会"认出"股票**：把股票代码、名称、日期匿名化后，85 对决策中有 12 对动作改变（14%，Kappa 0.57）。回测时必须考虑模型对历史行情的记忆。
3. **很多听起来合理的规律不成立**：
   - 限售解禁、股东减持、龙虎榜机构席位这三类避险因子，全部没有通过预先设定的回测门槛；
   - 价格行为信号中，只有"向上突破"和"高点、低点都在抬高的上升结构"通过了验证。
   - 新信号必须先只记录、不参与决策，验证通过后才能进入决策链。
4. **大模型自报的置信度普遍校准不佳**，所以必须用概率评分持续校准。

### 5.2 数据与记忆

1. **累计序列求和**：盘中累计资金流被逐点相加，数值膨胀约 100 倍，那段时期的评估数据整体作废。
2. **临时事故被当成长期知识**：一次数据源故障的记录被当作经验召回进决策上下文，不到一个月被召回 465 次。修法是对记忆按耐久性分类，并让情景事件过期。
3. **复盘记忆可能泄漏未来**：含有事后结果的复盘经验，如果被召回进当时的决策，就是变相使用未来数据。每条记忆必须标明"决策时可知"还是"事后才知"；结果可观测之前，相关记忆不得进入决策召回。
4. **终端乱码是假象**：数据其实是正确的 UTF-8，曾因此误判数据源损坏。验证中文要检查字符本身。

### 5.3 基础设施

1. **大模型服务是最大的单点故障**：所有后备模型共用同一个中继服务，中继断开约 4 小时，当天 5 个分析周期全部失败。后备链必须真正独立。
2. **嵌入式数据库不适合多线程并发写**：Windows 上多线程同时访问 DuckDB 出现过原生崩溃。必须坚持单写入者，慢操作不得占用写锁。
3. **全市场列表接口曾被定向封禁 4 天**：自己的重试和探测让封禁窗口一直滑动、冷却不下来。熔断期间必须一个请求都不发。

### 5.4 开发过程

1. **不做推测性的防御代码**：没有真实复现、调用链证据或失败测试的问题，只记录不修改。
2. **只保留一套现行口径**：结构调整原地替换并迁移数据，不并存"新旧两版"。
3. **控制付费运行**：代码、输入、协议都没变且已有成功结果时，不重复调用付费接口；批量调用前先说明预计次数。
4. **改共享组件前，先列出全部调用方**：新增的约束必须声明作用范围（主账户、对照组还是全部）。默认作用于全体，曾导致对照组被误伤。

## 六、目标系统

### 6.1 技术选型

- Python，版本满足 AgentScope 要求。
- **AgentScope**：
  - 用 ReAct 智能体实现各分析角色；
  - 每个角色配自己的工具包；
  - 多智能体协作用消息中心或流水线；
  - 复杂任务用计划本拆解；
  - 会话状态持久化。
- **ReMe**：长期记忆，包括经验、操作规则和用户偏好。
- **DuckDB**：交易与研究账本，单写入者。
- **APScheduler**：调度。
- **pydantic**：配置与结构化输出校验。
- 大模型：【待填：提供商、主模型、后备模型】，后备模型尽量来自独立的服务。
- 运行平台：【待填】；通知方式：【待填：邮件或某种推送】。

### 6.2 参考系统到目标系统的映射

| 参考系统 | 目标系统 |
|---|---|
| TradingAgents-CN 加自建多智能体运行时（两层） | 只用 AgentScope 一层，直接实现分析角色；可参考 TradingAgents-CN 的角色划分，但不嵌入它 |
| 自建工具注册表与角色工具包 | AgentScope 工具包 |
| 自建邮箱、交接、会话、步骤 | AgentScope 消息中心、流水线与会话状态；交接结果和决策仍落库，便于审计 |
| 自建两阶段记忆管道 | ReMe，外加本文要求的时间元数据与召回过滤 |
| 自建上下文管理和会话笔记 | 优先使用框架能力，但保留"压缩失败即中止、不得截断顶替"的纪律 |
| 多凭据池分级路由 | 一个主模型加一个独立后备，按任务重要性分两级 |
| Windows 服务加看门狗 | 按运行平台选用系统服务管理（Windows 服务或 systemd） |

### 6.3 必须保留的设计

1. 数据层的全部原则（见数据采集需求文档）。
2. 模拟券商的真实规则：下一交易日开盘成交、T+1、整手、涨跌停、完整费用、先进先出批次、成交后审计。
3. 交易日历守卫：核实不了就不交易。
4. 对照组账户（买入持有、随机、等权排名），从第一天起就与主策略并行运行。
5. 每条推荐都输出"未来 20 日跑赢沪深 300"的概率，并持续评分。
6. 决策时点纪律贯穿全系统：数据、证据、记忆一律只用决策时点前可见的部分。
7. 确定性守卫：数据质量门、仓位上限、资金纪律、交易权限。大模型的建议必须过闸门才能变成订单。
8. 不静默原则：每一处降级都有标记，每一次失败都有记录。
9. 大模型不可用时整轮跳过，不用规则冒充。

### 6.4 ReMe 接入的特别要求

1. 每条记忆必须带：产生时间、生效时间、耐久性分类（操作规则、持久事实、情景事件），以及"决策时可知"或"事后才知"的标记。
2. 决策召回只返回产生时间早于决策时点的记忆；情景事件超过有效期（参考值 5 天）不进入决策召回。
3. 含有事后结果的复盘经验，在结果可观测时间之前，不得进入决策召回。
4. 回测时，记忆库必须按时间点回滚，只使用当时已存在的记忆。
5. 行情数据和数据源故障不写入长期记忆；数据源的当前状态以健康台账为准。
6. 初期只把经过验证的操作规则写入长期记忆。

### 6.5 先简化或暂不做

- 角色先精简到 4–5 个：盘面与技术面、基本面与新闻、宏观政策与行业、风险复核、组合决策。
- 暂不做：外部监督代理插件、多凭据池路由、冷热分层存储、人工标注黄金集、Rust 资源监控、浏览器搜索。
- 执行实验账户和独立策略账户，在主策略与三个对照组稳定运行之后再加。

### 6.6 建议的开发顺序

每一步都可以独立运行和验收，后一步依赖前一步：

1. 数据采集层（按独立需求文档）。
2. 模拟券商、账本、交易日历守卫、三个对照组账户、每日估值。这一步不需要大模型，完成后第一天就有基准可比。
3. 大盘状态判断、候选初筛、技术特征预计算。
4. 研究证据包：结构化数据部分。
5. AgentScope 多角色分析：结构化输出买入、持有或卖出，外加概率；确定性守卫。
6. 组合计划、订单闸门、生成待成交订单、成交与审计。
7. 评估：前瞻收益、概率评分、与对照组比较、小样本统计。
8. 调度与自动运行、报告与通知。
9. 接入 ReMe 记忆（按 6.4 的要求）。
10. 扩展：文本证据链、盘中信号收件箱、事件触发、执行实验账户。

## 七、设计原则（全系统通用，冲突时按序号优先）

1. **不使用未来数据**：数据、证据、记忆一律以决策时点为界。
2. **不编造**：缺失就是缺失；不确定的事实要核实，不得臆测。
3. **不静默**：
   - 必要的降级要有理由，并在日志和结果字段里都带醒目标记；
   - 失败要记录；
   - 任何决策都不得悄无声息地发生。
4. **可追溯**：从研究、推荐、订单、成交到估值，用同一个周期编号串联；被拒绝和过期的信号保留，不删除。
5. **大模型负责解释，代码负责否决**：硬约束用确定性代码实现，不依赖提示词。
6. **能力默认开启**：默认关闭的功能等于没写。但真实下单永远关闭。
7. **以研究和决策效果为准**：不以省钱为目标做取舍，也不以账户金额小为由裁剪研究范围。但付费运行不得无意义重复。
8. **只保留一套现行口径**：不并存新旧两套结构或流程。

## 八、术语

| 术语 | 含义 |
|---|---|
| 决策时点 | 做决策时所站的时刻（北京时间）；只能使用这个时刻之前可见的信息 |
| 可见时间 | 一条信息最早可以被知道的时刻 |
| 对照组 | 和主策略走同一套模拟规则的基准账户，用来判断主策略是否真有选股能力 |
| 订单闸门 | 把交易计划变成订单之前，基于最新账户状态的最后一道确定性检查 |
| 正常冗余 | 同一份数据换一个来源获取，允许自动切换，但必须标注来源 |
| 降级 | 用质量更低的数据或模型顶替，必须显式允许并带标记 |
| 翻转率 | 同一输入下，两个版本给出不同动作的比例 |
| 观察窗 | 只有这个日期之后的结果才参与评估结论 |

## 九、协作方式

### 9.1 第一次回复

第一次回复时不要写代码，只输出以下内容：

1. 用你自己的话复述：业务目标、系统的核心闭环（数据 → 初筛 → 证据 → 分析 → 计划 → 闸门 → 订单 → 成交 → 估值 → 评估）、第七节的设计原则。
2. 你认为本文档中不明确、相互矛盾或不合理的地方，并附上你的建议。
3. 需要我做的决策清单，包括第六节的【待填】项。
4. 你对第六节开发顺序的意见。

### 9.2 后续每项开发任务

1. 先确认范围；非简单任务先给出设计，经我确认后再写代码。
2. 严格按范围实现，不擅自增加功能。遇到文档没有覆盖的情况，先按第七节的原则处理，并在交付时说明；如果影响设计，先问我。
3. 修改共享组件（券商、仓位、日历、数据链）之前，先列出全部调用方；新增的约束要写明作用范围。
4. 测试分两类：
   - 用受控输入测试自己的逻辑；
   - 真实联网测试单独标记、默认不运行。
   - 不允许通过模拟外部接口的响应，来证明"采集或集成正确"。
5. 交付时如实报告：测试失败就贴出失败输出；跳过了什么就说明跳过了什么；已知限制和代码缺陷分开写。
6. 需要批量调用付费大模型时，先说明预计调用次数并征得我同意；代码、输入、协议都没变时，不重复运行。
7. 外部接口、框架接口、字段名一律先查证再使用，不凭记忆猜测。
